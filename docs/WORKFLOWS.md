## Important: workflow-file edits can execute workflows

A documentation-only edit to a workflow YAML file is still a change to that workflow's configured `push.paths` filter. If the file itself is listed there, even a comment-only commit to `main` can start the workflow and perform its normal provider calls or repository writes. The same applies to implementation files listed in another workflow's path filter.

Before editing any workflow YAML or path-filtered implementation on the default branch:
1. Inspect every workflow whose `push.paths` may match the changed path.
2. Identify provider calls, repository writes, playlist side effects, concurrency groups and expected duration.
3. Prefer preparing the documentation change on a non-default branch and review the exact merge-trigger behavior before publishing.
4. Monitor every triggered run through completion and record any generated-data commits or failures.
5. Never assume a comment-only change is operationally inert.

## Tricky Daily force/idempotency discrepancy

The current `scripts/spotify/spotify_daily_cycle.py` passes `args.force` into both `should_run_cycle()` and `cycle_already_completed()`. The latter returns `False` immediately when `force=True`, so a forced invocation bypasses the same-Eastern-date completion guard as well as the clock window. The current schedule test explicitly asserts this behavior. This is broader than the intended Tricky Daily P0 contract: force should bypass the time-window gate only, while duplicate-date/idempotency, blacklist, whitelist reconciliation, lock, backup, validation and read-back checks remain in force. Treat the current behavior as an unresolved implementation discrepancy, not as an approved requirement. Feature code/test correction is deferred until the documentation-only pause ends; see [TRICKY_DAILY_TODO.md](TRICKY_DAILY_TODO.md) and the [Tricky Daily roadmap](../project/goals/tricky-daily/ROADMAP.md).

## Important operational distinctions

- **Read-only validation:** daily-curator-tests.yml, library-freshness-review.yml, playlist-fit-preview.yml, playlist-manager-check.yml, public-repository-security.yml, spotify-daily-live-preflight.yml and spotify-daily-remote-verification.yml are intended as checks/previews, not playlist writers.
- **Playlist write-capable workflows:** spotify-daily-midnight-cycle.yml and spotify-playlist-manager.yml can mutate Spotify playlists. Follow their explicit locks, ownership checks, staging, confirmation, audit, and live read-back requirements. The Daily exception does not authorize arbitrary personal playlist writes.
- **Repository/data writers:** update.yml, enrich-music-metadata.yml, acoustic-metadata-enrichment.yml, backfill-music-durations.yml, great-migration.yml, spotify-daily-feedback-observation.yml and spotify-reference-library.yml can commit repository state. Inspect their exact target paths and publication/rebase safeguards before changing them.
- **Authentication and secret rotation:** several Spotify workflows mint a narrowly scoped GitHub App token to persist a rotated refresh token. Document only the variable/secret names and permission boundary, never values.
- **Schedule interpretation:** cron expressions are UTC. Tricky Daily has explicit Eastern-time DST handling in TRICKY_DAILY_CYCLE.md; do not infer local midnight from a UTC cron without reading that guide.
- **Evidence:** a workflow run's success means its declared job completed. It does not automatically prove live Spotify read-back or a playlist mutation unless the workflow explicitly performed and recorded that verification.
